## 4. 失败项定位与修复记录

### F-1（测试缺陷，已修复并复测）

- 编号/任务：T-010「恢复—索引与约束」。
- 测试文件：`tests/scripts/test_backup_restore.sh`（初版）。
- 现象：初版用 `sqlite3 --readonly "$RESTORE_DB" "INSERT ... role='superuser' ..."` 后断言
  「退出码非 0」，但 `--readonly` 会让**任何**写入失败，该断言实际只证明“只读连接拒绝写入”，
  并未证明 `CHECK` 约束被保留，属**错误前提/无效断言**。
- 问题分类：测试缺陷（非实现缺陷）。
- 根因：测试用只读连接做“违反约束”的写入，混淆了失败原因。
- 修复：改为可写连接执行非法插入，断言退出码非 0 **且**错误信息包含 `CHECK`；随后复测。
- 复测结果：T-010 的 4 项断言全部通过。修复仅针对测试脚本，未改动 `scripts/backup.sh`。

未发现 `scripts/backup.sh`、`README.md`、`.gitignore`、`backup/.gitkeep` 的实现/文档缺陷。

**遗留限制（如实记录）**：`SIGKILL` 不可被捕获，故 `backup.sh` 被 `SIGKILL` 时其导出的子进程
（`timeout`/`sqlite3`）与临时文件不会被父进程清理，会持续到外层 `OJ_BACKUP_TIMEOUT`（默认 600s）
到期；本测试按**唯一临时库路径**清理了该残留子进程。此路径不影响正式备份文件（不会产生）、
源库完整性（`ok`）与并发锁（OS 自动释放）。此为 shell 包装器在不可捕获信号下的固有边界，
非正式文件/源库安全缺陷。

## 8. 真实 cron 守护进程调度（操作检查）

在隔离路径下临时安装一条可逆的每分钟任务（结束后已恢复为“无 crontab”）：

```cron
SHELL=/bin/bash
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
OJ_BACKUP_TZ=UTC
* * * * * bash /home/xay/Object/Vibe-Coding/scripts/backup.sh --db <隔离库> --out-dir <隔离目录> >> <隔离日志> 2>&1
```

证据（守护进程确实执行）：

- 安装时间 `2026-09-24T23:44:37+08:00`；**24s 后**（23:45:01）由 cron 执行。
- 生成 `backup/oj-20260924.sql`，权限 `-rw-------`（0600）。
- cron 日志（UTC，因 `OJ_BACKUP_TZ=UTC`）含「备份完成」、源库 92 KiB、表数 6、耗时 0s。
- 将该定时备份导入新库：`import_ok`，`integrity_check=ok`。
- 检查后 crontab 已移除（`crontab -l` → `no crontab for xay`），无临时目录/进程残留；
  全程未触碰仓库 `data/oj.db` 或正式服务。

结论：cron 示例在真实守护进程中可被调度执行，且不依赖交互终端 cwd/隐式配置。
