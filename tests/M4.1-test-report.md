## 四、失败项定位与修复

### F-1：非法参数路由被 not-found 兜底覆盖（实现缺陷，T-21）

- 触发：`#/problems/%E0%A4%A`；涉及 `renderBadAddress`（web/js/router.js:243）。
- 预期「地址参数无效」，实际「页面不存在」；根因是非法参数与未知路由共用 not-found 兜底。
- 修复：非法参数跳过兜底并输出「地址参数无效」。复测 M41-2 通过。

### F-2：M2.5 jsdom harness 未暴露 sessionStorage（测试缺陷，T-40）

- S4 起 20 项级联失败；根因是 M4.1 的 `storage.js` 使用全局 `sessionStorage`，旧 harness
  只绑定了 `localStorage`。
- 修复：`tests/frontend/admin_pages_dom.mjs` 增加 `globalThis.sessionStorage = window.sessionStorage`。
  复测 128/128 通过。
- 已确认需求变化：S4 期望由「改密后 `#/problems`」更新为「回原目标 `#/admin`」（M4.1 第 16 条）。

### F-3：M41-13 测试辅助逻辑产生未处理拒绝（测试缺陷，T-时序）

- 现象：M41-13 报 `unhandledRejection: AbortError`。
- 根因：晚返回时 `resolve(orig(input, init))` 采纳了请求被 abort 后已拒绝的 Promise，
  该拒绝无处理者。
- 修复：以 `orig(...).then(resolve, reject)` 接管底层请求（生产代码无缺陷）。复测 M41-13
  及全套 45/45、逻辑 73/73 通过。

## 六、加载问题定位（Windows 转发后页面空白/一直加载）

- **服务端有明确超时的请求**：对实际监听端口 8080，`/api/health`、`/`、`/index.html`、
  `/css/styles.css`、`/js/*.js`（含全部页面模块）、`/api/problems` 均返回 `200`，耗时
  < 2ms，MIME 正确（HTML `text/html`、CSS `text/css`、JS `application/javascript`、
  API `application/json`）；`/api/me` 无 token 返回 `401`；未知路径 `404`。服务未卡住。
- **真实浏览器整页加载**（Linux 无头 Chromium，实际 Chromium 内核）：23/23 资源全部
  `200` + 正确 MIME，**0 个 pending 请求、0 条 Console/Page 错误**；无 token 渲染题目
  列表，伪造 token 渲染登录页并清理凭证。M4.1 的身份初始化、`/api/me`、路由守卫与
  `render()` 未出现等待或异常导致的加载停滞。
- **已确认根因**：转发目标当时**没有正在运行的 `oj_server`**（本机无进程、8080 未监听）。
  服务存在两个“启动即退出”的常见原因，均可复现为转发后空白/加载：
  1. 判题工作目录非 tmpfs：未设 `OJ_JUDGE_WORKSPACE` 且 `/opt/oj-tmpfs` 未挂载时，
     启动检查失败，退出码 1；
  2. 首次初始化数据库未设 `OJ_ADMIN_PASSWORD`：初始化失败，退出码 1。
- **修复（针对已确认原因）**：新增 `scripts/run_dev_server.sh`，自动为判题选择可用的
  tmpfs（`/opt/oj-tmpfs` → `/dev/shm` → 显式非 tmpfs 告警），并在首次初始化缺
  `OJ_ADMIN_PASSWORD` 时**直接报错退出**而不是静默失败；启动后打印监听地址与自检命令。
  README 增加启动排错与 `curl /api/health` 自检说明。该改动不涉及权限检查或身份初始化。
- **防御性加固**：`web/js/api.js` 为所有请求增加 15s 超时（`DEFAULT_TIMEOUT_MS`，可被
  `timeoutMs` 覆盖）。后端不可达/连接被接受却无响应时抛出明确超时错误（`timeout:true`,
  `network:true`, `status:0`），页面据此显示失败并可重试，不再永久停在「加载中」；超时
  不清理本地 token（无假登出）。写请求仍按“结果无法确认、不自动重试”处理。
- **原失败场景复测（真实浏览器）**：用请求拦截模拟“连接被接受但永不响应”——
  - `/api/problems` 挂起：约 15.3s 后页面显示「题目加载失败：网络连接失败…重试」，
    不再无限加载；
  - `/api/me` 挂起：约 15.3s 后身份核实失败并按游客处理，页面恢复可操作；
  - 直接探针确认超时分类为 `timeout=true/network=true/status=0`，且 **token 未被清除**。
- **新增用例**：逻辑 T-14（无响应请求按超时返回、超时快速返回、主动取消仍归 aborted），
  逻辑总数 73 → 76；其余 M4.1 DOM 45/45、M2.5 回归 128/128、真实浏览器 37/37 均复测通过。
- **Windows 转发实测（用户手动）**：修复后经 VS Code/SSH 端口转发访问，页面正常显示登录
  界面；输入 `admin`/初始密码后按要求进入改密页；改密成功后进入主页面。该链路
  （游客 → 登录 → 首次强制改密 → 进入主页面）在 Windows 真实浏览器上复现通过，原“空白/
  一直加载”失败场景不再出现。
- **有头模式完整场景（服务器本机）**：以 Xvfb 虚拟显示（1280×800×24）运行
  `playwright-cli open --headed` + 同一 M4.1 场景脚本，真实 Chromium **有头**执行
  **37/37 通过、0 脚本错误**，生成 6 张截图（桌面题目列表/题目页/后台首页、360×640 /
  390×844 / 768×1024 题目页）。截图中文显示为方框仅因服务器未装 CJK 字体，非页面缺陷。
- **未验证项（本轮范围）**：上述有头运行在**服务器虚拟显示**完成，不等同于 Windows 有头；
